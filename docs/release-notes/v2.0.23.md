## 2.0.23 — Ambient Work Mode

Ambient Work Mode provides a compact view of MALACHI OVERDRIVE's real task activity while work
continues in an isolated browser surface. The right-edge capsule opens a non-modal preview; the
full Control Rail workbench opens only when requested. The composer and the rest of the app remain
available throughout.

- Desktop sends, workers, continuations and automatic helper chats use one isolated placement
  path. Ordinary chat-opening preferences cannot authorize taking over a personal tab. If the
  matching companion or isolation proof is unavailable, browser actions fail with a clear error.
- Full browser restart is a deliberate recovery limit. Ownership survives companion suspension
  in the same browser session, but a restored minimized window or matching conversation alone
  does not prove ownership after restart. Unproven surfaces fail with `BACKGROUND_UNAVAILABLE`;
  task history is retained, with no automatic resend or false completion. A new isolated tab is
  allowed only by a fresh durable opening request that remains proven safe to execute.
- Activity presents confirmed task state, model and reasoning identity, workers, outputs and
  actionable problems. Progress is shown only when supported by real task data.
- Closing the preview leaves work running. Task controls resolve the selected task against current
  engine state, and completion feedback follows a genuine completed transition.
- Keyboard controls, focus restoration, reduced motion and narrow layouts remain part of the
  compact experience.
- Physical screen, keyboard, mouse and clipboard access requires an explicit foreground handoff
  for the selected live turn. Stop, a new turn and app restart invalidate that handoff. Queued
  native actions recheck permission before execution; app and operating-system grants still apply.
- Pause prevents automatic follow-ups while the current reply may finish. Stop targets the
  selected turn; other worker tasks remain independent. Ambiguous sends are never silently retried.
- The native Windows UI Automation smoke test now queries its own known window and button. An
  unrelated foreground program can no longer determine which provider that test exercises.

### Validation

Local release validation is complete: `verify:ci` passed with 3,568 tests and the expected 106
platform/live skips; privacy, notices/corresponding-source, TypeScript and Electron-load gates all
passed. The production renderer QA passed 77 assertions at desktop and 390/320 px widths with no
console errors, forbidden actions, modal scrim, horizontal overflow or external HTTP/HTTPS/WebSocket
requests. A native Apple-silicon package also passed resource/native-runtime, bundle/Mach-O, DMG,
ZIP and isolated-profile GUI-startup checks.

The unpublished 2.0.22 candidate correctly stopped before release when both Windows runners again
failed the exact owned-button UI Automation assertion; Linux x64/ARM64 and both signed/notarized
macOS lanes were green, so candidate assembly and publication remained skipped. The remaining
problem was not a longer accessibility-publication delay: the fixture process deliberately hides
its PowerShell console, and the managed WinForms child provider was not a stable ControlView fixture
on the hosted Windows desktops even after both HWNDs were visibly created. 2.0.23 keeps the
production desktop helper unchanged and replaces that fixture with an all-native owned Win32 window
plus Windows' standard `BUTTON` control. The parent is shown without activation, both native HWNDs
must be visible with non-zero bounds, and the test then performs one exact production `find_ui`
query. No unrelated foreground application or timing retry is used.

The public release remains gated on all six native CI jobs. Candidate assembly may happen only
after every platform job is green, including installing and normally launching both generated
Windows NSIS packages, Developer ID signing and Apple notarization for both macOS architectures,
and checksum coverage for every payload beside `SHA256SUMS.txt`. After publication, the publish job
requires the exact 13-asset set, re-downloads the public files, matches the public checksum manifest
back to the candidate and verifies every payload digest again. The updater must then detect the
published version, and the official signed ARM64 build must be installed and reconnected to its
matching browser companion before this release is considered complete.

Public macOS artifacts require Developer ID signing and Apple notarization for both architectures.
They preserve the existing bundle identifier and signing team. macOS 13 Ventura or newer is required.
Reload the matching protocol-15 browser companion after updating. Existing pairing is preserved.

Linux AppImage installations use the bundled static runtime. Where unprivileged user namespaces
are disabled, that runtime can fall back to `--no-sandbox`. The `.deb` stays under the system
package manager's control.

Model admission remains fail-closed. A requested model or reasoning level is never silently
substituted; an unavailable combination is reported as unavailable.
