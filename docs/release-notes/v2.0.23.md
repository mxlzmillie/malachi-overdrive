## 2.0.23 — Background browser reliability

This update repairs the browser-window ownership failures and tab buildup seen after ordinary
task use and Opera restarts. It builds on the Ambient Work Mode released in 2.0.22.

- Revealing one task moves only its exact tab to a visible window. Sibling tasks remain isolated
  in the background window and keep receiving their own work.
- Live tab IDs are retained even after hundreds of helper openings and closings. A still-open task
  can no longer be evicted from the app-owned window's registry by an old 200-ID cache limit.
- After a full Opera restart, the companion popup can reconnect the exact selected task chat on
  an explicit click. It checks app ownership and an idle, draft-free page, moves that same tab
  into an isolated minimized window and never opens a replacement or replays an uncertain send.
- A matching but unowned chat blocks an automatic duplicate opening. The error now explains the
  popup recovery action instead of saying to reconnect an already connected companion.
- Quiet app-owned task tabs are capped at eight after a minute of inactivity. Active work, pending
  sends and drafts remain protected; each close still requires fresh document and page proof.
- Empty app-owned helper tabs from finished or failed operations retire after a separate minute
  of confirmed inactivity and a fresh no-draft/no-generation proof. One warm catalog helper stays
  available for model discovery.
- The owned Windows UI Automation release test checks the exact control and role filter using the
  role the host provider reports. This preserves coverage across both Windows architectures.

### Validation

Local `verify:ci` passed: 3,584 tests plus the 2 shutdown tests, with 106 expected platform/live
skips. Privacy, license/native-source notices, TypeScript, Electron loading, JavaScript syntax and
the production bundle build also passed. The six native candidate jobs remain the publication gate.
The previously failing 2.0.23 Windows candidate found its exact owned child
in UI Automation, but the host reported it as `Pane` while the test required `Button`. The test now
checks the exact name, automation ID, bounds and semantic ref, then verifies role filtering against
the observed role and a negative role case. The production UI Automation implementation is unchanged.

The public release remains gated on all six native CI jobs. Candidate assembly may happen only
after every platform job is green, including installing and normally launching both generated
Windows NSIS packages, Developer ID signing and Apple notarization for both macOS architectures,
and checksum coverage for every payload beside `SHA256SUMS.txt`. After publication, the publish job
requires the exact 13-asset set, re-downloads the public files, matches the public checksum manifest
back to the candidate and verifies every payload digest again. The updater must then detect the
published version, and the official signed ARM64 build must be installed and reconnected to its
matching browser companion before this release is considered complete.

Public macOS artifacts require Developer ID signing and Apple notarization for both architectures.
They preserve the existing bundle identifier and signing team. macOS 13 Ventura or newer is required.
Reload the matching protocol-15 browser companion after updating. Existing pairing is preserved.

Linux AppImage installations use the bundled static runtime. Where unprivileged user namespaces
are disabled, that runtime can fall back to `--no-sandbox`. The `.deb` stays under the system
package manager's control.

Model admission remains fail-closed. A requested model or reasoning level is never silently
substituted; an unavailable combination is reported as unavailable.
